- 2026-10-03 (Session 10 deployment prep, no-auth): The deployed Render + Vercel instance ships without authentication. Rationale: the dataset is derived entirely from public-domain annual reports plus already-published composite scores, so there is nothing private to protect; adding an auth system would introduce an attack surface, operational burden (password resets, session storage, user table), and compliance considerations (session cookies, PII) with no corresponding risk reduction. CORS is still restricted to the Vercel origin via `ALLOWED_ORIGINS` so random browser callers can't programmatically pound the API from third-party sites, and Render's free tier naturally rate-limits via its request budget. If/when the project moves to accepting user-submitted data (benchmark CSV upload beyond the current admin-only path, or taxonomy edits via the UI), auth must be reinstated before that endpoint is exposed. Decision owner has signed off on this trade-off explicitly.
- 2026-10-03 (Session 7 hard-limits audit, resolution of the 92 sub-2s crawl_log deltas): Full breakdown of every one of the 92 flagged rows: 61 at delta=0.00s (40 `blocked`, 10 `ok`, 10 `existing sha256 …` dedupe log rows, 1 `not_found`, 1 `robots_disallowed`, 1 misc) and 31 at delta=1.00s (18 `ok`, 12 `existing sha256 …` dedupe, 1 `not_found`). No other sub-2s bucket. Reading `app/crawler/fetch.py` directly: `get()` (line 150) short-circuits `self._blocked` and `self._robots_allow` BEFORE calling `_wait()`, so pre-blocked / robots-disallowed rows legitimately bypass the delay helper (they open no socket). `_get_requests` (line 162 → 166) and `_get_playwright` (line 219 → 221) BOTH call `self._wait(host)` on every real-network request. `_wait()` sets `self._last_hit[host]` AFTER the sleep but BEFORE the fetch fires, so the 2-second floor is enforced between request *starts*. The audit was comparing crawl_log `at` timestamps, which record *completion* time — if request 1 is slow and request 2 is fast, start-to-start can be ≥ 2 s (legal) while completion-to-completion is sub-2 s. The `existing sha256 …` rows are a second log line written in the same second as the fetch that produced them. **Finding, stated plainly**: audit's framing was wrong (completion-delta instead of start-delta); the Fetcher correctly enforces the 2-second same-domain floor on request starts in every path that touches the network; zero of the 92 flagged rows represents a true <2 s network request. The follow-up is a CrawlLog schema change (store `start_at` + distinguish `pre_blocked_skip`), tracked in `docs/BACKLOG.md`. No scoring or data impact.
